この記事の手順は 2026年11月28日 に下記の環境で実際に実行して確認しました。

## 結論：まだ push していないなら git reset、push 済みなら git revert で取り消します

`git reset` は「ブランチの位置を前のコミットに戻して、コミットを履歴からなかったことにする」コマンドです。`git revert` は「取り消したいコミットと逆の変更を、新しいコミットとして追加する」コマンドで、履歴は消えません。
手元だけにあるコミットなら `git reset`（変更を残したいなら `--soft` か何も付けない、変更ごと捨てるなら `--hard`）、すでに push して他の人も持っているコミットなら `git revert` を使うのが基本です。
この環境では、push 済みのコミットを `git reset` で消してから push すると `! [rejected]` で拒否され、`git revert` なら普通に push できることを確認しました。

```text 実行ログ
$ git revert --no-edit HEAD && git log --oneline && ls
[main 26cf0d3] Revert "デバッグ用のログを追加（間違い）"
 Date: Fri Nov 27 21:48:44 2026 +0000
 1 file changed, 1 deletion(-)
 delete mode 100644 debug.log
26cf0d3 Revert "デバッグ用のログを追加（間違い）"
9f6cceb デバッグ用のログを追加（間違い）
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
calc.py
```

## 検証環境

| 項目 | バージョン |
|---|---|
| OS | Ubuntu 24.04.5 LTS |
| Git | git version 2.43.0 |

同じパソコンの中に、GitHub の代わりになるリモート用のリポジトリ（`remote.git`）と、それを clone した作業用のリポジトリ（`app`）を作って試しました。お使いの環境（OS・バージョン）が違うと、出力やエラー文が少し変わることがあります。

## 状況の再現：間違ったコミットをしてしまった

`calc.py` に関数を書いてコミットし、動作確認用の行を足してもう1回コミットしたあと、入れるつもりのなかった `debug.log` までコミットしてしまった、という状況を作りました。

```text 実行ログ
$ printf "debug: test run\n" > debug.log && git add debug.log && git commit -q -m "デバッグ用のログを追加（間違い）" && git log --oneline
9f6cceb デバッグ用のログを追加（間違い）
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
```

一番上の `9f6cceb` が取り消したいコミットです。このコミットを、まだ push していない場合と、push したあとの場合に分けて取り消します。

## 原因：reset は履歴を消し、revert は履歴に足す

2つのコマンドは、取り消し方がまったく違います。

- `git reset HEAD~1` は、ブランチの先頭を1つ前のコミット（`HEAD~1`）に動かします。取り消したコミットは `git log` から見えなくなります。手元の履歴を書き換えるので、まだ誰にも渡していないコミットに向いています。
- `git revert HEAD` は、指定したコミットの変更を打ち消す「逆向きのコミット」を新しく作ります。元のコミットも履歴に残るので、ほかの人が持っている履歴と食い違いません。

さらに `git reset` には、取り消したコミットの変更をどこに残すかで3つのモードがあります。次の節で、同じコミットに対してそれぞれ実行した結果を並べます。

## 直し方1：push 前なら git reset（3つのモード）

### --soft：コミットだけ取り消し、変更はステージに残す

```text 実行ログ
$ git reset --soft HEAD~1 && git log --oneline && git status --short
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
A  debug.log
```

`git log` から `9f6cceb` が消え、`git status --short` に `A  debug.log` と出ました。`A` は「ステージ（git add 済み）に入っている」という印です。コミットメッセージだけ直したい、別のファイルも足してコミットし直したい、というときに使えます。

### 何も付けない（--mixed）：コミットと git add を取り消し、ファイルは残す

もう一度同じコミットを作り、今度はオプションなしで `git reset` しました。オプションを付けないと `--mixed` と同じ動きになります。

```text 実行ログ
$ git commit -q -m "デバッグ用のログを追加（間違い）" && git reset HEAD~1 && git log --oneline && git status --short
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
?? debug.log
```

今度は `?? debug.log` になりました。`??` は「Git が管理していないファイル」という意味で、`git add` も取り消されています。ファイル自体はフォルダに残っているので、「間違ったファイルをコミットに入れてしまった」ときはこのモードが分かりやすいです。

### --hard：コミットも変更も捨てる

```text 実行ログ
$ git add debug.log && git commit -q -m "デバッグ用のログを追加（間違い）" && git reset --hard HEAD~1 && git log --oneline && git status --short && ls
HEAD is now at 5b6be7f 動作確認の print を追加
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
calc.py
```

`ls` の結果から `debug.log` が消えました。`--hard` は作業中のファイルまでコミットの時点に戻すので、取り消したコミットの変更はフォルダからなくなります。

### --hard で消しすぎたときは git reflog で戻せる

`git reflog` には、HEAD が動いた記録が残っています。`HEAD@{1}` が「reset する直前」の位置でした。

```text 実行ログ
$ git reflog -4
5b6be7f HEAD@{0}: reset: moving to HEAD~1
9f6cceb HEAD@{1}: commit: デバッグ用のログを追加（間違い）
5b6be7f HEAD@{2}: reset: moving to HEAD~1
9f6cceb HEAD@{3}: commit: デバッグ用のログを追加（間違い）

$ git reset --hard HEAD@{1} && git log --oneline && ls
HEAD is now at 9f6cceb デバッグ用のログを追加（間違い）
9f6cceb デバッグ用のログを追加（間違い）
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
calc.py
debug.log
```

コミットと `debug.log` の両方が戻りました。ただし、戻せるのはコミットしたことのある内容だけです。一度もコミットしていない変更を `--hard` で消した場合は、reflog にも残りません。

## 直し方2：push 済みなら git revert

次に、このコミットを push してから取り消します。

```text 実行ログ
$ git push -q origin main && git log --oneline origin/main
9f6cceb デバッグ用のログを追加（間違い）
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
```

`git revert --no-edit HEAD` を実行すると、`Revert "デバッグ用のログを追加（間違い）"` という新しいコミット `26cf0d3` ができ、`debug.log` が消えました（実行ログは記事の冒頭のとおりです）。`--no-edit` は、Git が用意したメッセージのままコミットするオプションです。中身を見ると、`debug.log` を削除するだけのコミットになっていました。

```text 実行ログ
$ git show --stat --format="%h %s" HEAD
26cf0d3 Revert "デバッグ用のログを追加（間違い）"

 debug.log | 1 -
 1 file changed, 1 deletion(-)

$ git push origin main
To /tmp/run-h-0051/work/remote.git
   9f6cceb..26cf0d3  main -> main
```

履歴に足しただけなので、push はそのまま通りました。別の場所で clone し直しても、取り消しのコミットが入った履歴が届いています。

```text 実行ログ
$ git clone -q remote.git other && cd other && git log --oneline && ls
26cf0d3 Revert "デバッグ用のログを追加（間違い）"
9f6cceb デバッグ用のログを追加（間違い）
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
calc.py
```

## うまくいかないとき

- **push 済みのコミットを git reset で消すと、push が拒否されます。** 試しに `git reset --hard HEAD~2` で2つ前に戻してから push したところ、`! [rejected] main -> main (non-fast-forward)` になりました。手元の履歴がリモートより古くなったためです。`git reset --hard origin/main` でリモートと同じ状態に戻してから、`git revert` で取り消し直してください。

```text 実行ログ
$ git push origin main
To /tmp/run-h-0051/work/remote.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to '/tmp/run-h-0051/work/remote.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

$ git reset --hard origin/main && git log --oneline
HEAD is now at 26cf0d3 Revert "デバッグ用のログを追加（間違い）"
26cf0d3 Revert "デバッグ用のログを追加（間違い）"
9f6cceb デバッグ用のログを追加（間違い）
5b6be7f 動作確認の print を追加
0509b77 合計を計算する関数を追加
```

- **一番新しいコミット以外も revert できます。** `HEAD~2`（HEAD から2つ前）の「動作確認の print を追加」を指定したところ、そのコミットで足した2行だけが `calc.py` から消え、あとのコミットはそのまま残りました。コミットのハッシュ（例 `git revert 5b6be7f`）で指定しても同じです。

```text 実行ログ
$ git revert --no-edit HEAD~2 && git log --oneline -3 && cat calc.py
[main fd4b02b] Revert "動作確認の print を追加"
 Date: Fri Nov 27 21:48:44 2026 +0000
 1 file changed, 2 deletions(-)
fd4b02b Revert "動作確認の print を追加"
26cf0d3 Revert "デバッグ用のログを追加（間違い）"
9f6cceb デバッグ用のログを追加（間違い）
def total(prices):
    return sum(prices)
```

- revert で同じ行をあとのコミットが変えていると、`CONFLICT` が出て止まることがあります。直し方はマージの衝突と同じなので、[git merge で CONFLICT (content): Merge conflict in が出たときの解消手順](/h-0050/) をご覧ください。この記事では revert の衝突そのものは実行していません。
- `git push --force` で reset した履歴を無理に上書きする方法もありますが、ほかの人の履歴と食い違うため、この記事では扱っていません。オプションの意味は Git の公式ドキュメント（git-push）をご確認ください。

## まとめ

コミットの取り消しは、まだ push していなければ `git reset`、push 済みなら `git revert` が基本です。この環境では、`--soft` は変更をステージに、何も付けない `git reset` はファイルだけを残し、`--hard` は変更ごと消すこと、消しすぎても `git reflog` から戻せることを確認しました。push 済みのコミットを reset すると push が拒否されるため、その場合は revert で取り消しのコミットを足してください。
